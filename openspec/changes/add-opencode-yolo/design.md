## Context

See `proposal.md` for motivation. Relevant current-state facts this design builds on:

- The `Dockerfile` already installs `@anthropic-ai/claude-code` globally as the `node` user and is the single image `claude-yolo` builds; it also bakes in `git-wrapper.sh` (blocks `push`/`send-pack`), sudo, jq, tini, .NET SDKs, serena, and OpenSpec tooling.
- `claude-yolo` (the script) resolves its own symlink to find the Dockerfile, computes `PROJECT_DIR`, supports `--workspace`, and dispatches `yolo`/`run`/`rebuild`/`nuke` against a fixed `IMAGE`/`VOLUME` pair, with `docker run --rm -v "$PROJECT_DIR":/workspace -v "$VOLUME":/home/node ... "$IMAGE" "$@"`.
- `entrypoint.sh` does Claude-specific setup (host `~/.claude` sync, trust-dialog pre-accept, serena `.mcp.json` rewrite) before `exec tini -- "$@"`.
- opencode resolves its config from `opencode.json` at several locations, including `~/.config/opencode/opencode.json` (global) — see https://opencode.ai/docs/config/. A custom OpenAI-compatible provider is declared under `provider.<id>` with `npm: "@ai-sdk/openai-compatible"` and `options.baseURL`; usable models must be listed explicitly under that provider's `models` map (opencode does not query `/v1/models` itself) — see https://opencode.ai/docs/providers/. `opencode run --auto` / `opencode --auto` auto-approve everything not explicitly denied (opencode's equivalent of `--dangerously-skip-permissions`) — see https://opencode.ai/docs/permissions/. The bare `opencode` command only ever launches the interactive TUI; it does not accept a prompt positional itself (only `opencode run [message..]` does) — see https://opencode.ai/docs/cli/.
- An MLX server (or any other OpenAI-compatible local server) bound to `127.0.0.1:8000` on the host is not reachable from inside a container as `localhost:8000` — that address is the container's own loopback. Docker Desktop resolves `host.docker.internal` to the host automatically; plain Linux Docker Engine (20.10+) needs `--add-host=host.docker.internal:host-gateway` on `docker run` for the same mapping to exist.

## Goals / Non-Goals

**Goals:**
- Reuse the existing `Dockerfile`, git-push guard, `/workspace` mount convention, and baked tooling for a second script that drives `opencode` instead of `claude`.
- Make the default model "whatever the local server currently has loaded" rather than a name the user has to know and type.
- Keep `opencode-yolo` and `claude-yolo` fully independent at the image-tag and volume level so operating one never risks the other's build cache or persisted state.

**Non-Goals:**
- Mounting a host `~/.config/opencode` (or similar) the way `entrypoint.sh` mounts and merges `~/.claude` — no equivalent host-config sync is added in this change. opencode's config in the sandbox is entirely generated by `opencode-entrypoint.sh` plus whatever the user edits inside the running container (persisted via `opencode-yolo-home`).
- Supporting remote/authenticated model providers through `opencode-yolo` — this change only wires up a local, unauthenticated OpenAI-compatible server. Nothing prevents a user from running `opencode auth login` themselves inside the container for other providers; it's just not automated here.
- A `--preserve-token` option on `opencode-yolo nuke` (present on `claude-yolo nuke`) — there is no login/OAuth token to preserve for an unauthenticated local server, so `opencode-yolo nuke` only has the one (full-wipe) confirmation path.
- Handling a model server that reports more than one loaded model with any ranking beyond "first in the list" — MLX's own server (and most single-model local servers) only ever reports one; a multi-model proxy is out of scope.

## Decisions

**1. `opencode-ai` is installed into the *same* `Dockerfile`/image as Claude Code, via a new `OPENCODE_VERSION` build arg, rather than a second Dockerfile.**
Per the shared-image choice: both tools need the same git-push guard, sudo/jq/tini base, and (optionally) the .NET/serena/OpenSpec extras already baked in. Duplicating all of that in a second Dockerfile would double the maintenance surface for no isolation benefit — neither tool's install step touches the other's. Pin `OPENCODE_VERSION=1.18.34` (latest `npm view opencode-ai version` at the time of this change), matching the existing exact-pin style used for `CLAUDE_VERSION`/`OPENSPEC_VERSION`, and set `"autoupdate": false` in the generated `opencode.json` (see Decision 4) so opencode's own background updater can't drift off that pin, mirroring `DISABLE_AUTOUPDATER=1` for Claude Code.

**2. `opencode-yolo` builds and references its own `opencode-yolo` image tag and `opencode-yolo-home` volume, never `claude-yolo`'s.**
Alternative considered: have both scripts share one `claude-yolo`-tagged image, since the Dockerfile is identical either way. Rejected because it makes `claude-yolo rebuild`/`nuke` and `opencode-yolo rebuild`/`nuke` silently affect each other's image — confusing and risky (e.g. `opencode-yolo nuke` deleting the image `claude-yolo` depends on). Building the identical Dockerfile under two tags costs effectively nothing once the layer cache is warm (same content-addressed layers, just two tag pointers), so the isolation is free.

**3. `opencode-entrypoint.sh` is a separate script from `entrypoint.sh`, selected via `docker run --entrypoint`, not a mode flag inside the existing entrypoint.**
`entrypoint.sh`'s job (host `~/.claude` sync, Claude trust-dialog pre-accept, serena `.mcp.json` rewrite for Claude's MCP config shape) is entirely Claude-specific and irrelevant to opencode. Branching one script on "which tool am I" would make both halves harder to read for no shared logic beyond `exec tini -- "$@"`. The `Dockerfile` bakes both entrypoint scripts in; each run script picks its own via `--entrypoint`.

**4. Model discovery happens in `opencode-entrypoint.sh` at container start, by `curl`-ing `GET $MLX_BASE_URL/v1/models` and taking `.data[0].id` with `jq`, then merging that into `opencode.json` with `jq` (not overwriting the whole file).**
opencode has no built-in "discover models from this OpenAI-compatible server" behavior (confirmed above), so the sandbox does it once, at the point it already controls: container start, before `opencode` itself runs — the same point `entrypoint.sh` already uses for its own dynamic rewrites (serena's `.mcp.json`, the trust dialog). Writing is a `jq` merge (`.provider.mlx = {...} | .model = "mlx/" + $id` applied to the existing file, default `{}` if absent) rather than replacing the file outright, so any other settings the user has added inside a running container (e.g. `permission` overrides, other providers) survive the next restart on the persisted `opencode-yolo-home` volume — the same reasoning `entrypoint.sh` already applies to Claude's `settings.json`. The provider's `options.apiKey` is set to a fixed placeholder string (`"not-needed"`): the AI SDK's OpenAI-compatible client shape expects the field to be present, but MLX's server does not check it.

**5. `opencode-yolo` always passes `--add-host=host.docker.internal:host-gateway` on `docker run`, and the default `MLX_BASE_URL` is `http://host.docker.internal:8000`.**
This makes `host.docker.internal` resolve on plain Linux Docker Engine the same way it already does out of the box on Docker Desktop, so one code path works on both without detecting the platform. The flag is a documented no-op where the mapping already exists.

**6. `opencode-yolo`'s `yolo`/`run` modes pass trailing arguments straight to `opencode` (`opencode --auto "$@"` / `opencode "$@"`), without trying to detect "is this a prompt" and routing it through `opencode run` automatically.**
Alternative considered: make `opencode-yolo yolo "fix the bug"` behave like `claude-yolo yolo "fix the bug"` (a bare positional prompt). Rejected because the bare `opencode` command does not accept a prompt positional at all (only `opencode run [message..]` does, per opencode's CLI docs) — silently rewriting the user's trailing args into an `opencode run` invocation would be surprising if they passed something else (e.g. `--model` or `models`, opencode's own subcommand). Forwarding verbatim keeps the script a thin wrapper: `opencode-yolo yolo run "fix the bug"` is how a user gets opencode's headless mode, explicitly.

## Risks / Trade-offs

- **Two image tags for one Dockerfile means two `docker build` invocations to stay current** → mitigated by Decision 2's point that a cache-warm second build is near-instant; documented in the proposal's Impact section so it isn't a surprise.
- **The model server being down or slow at container start** → mitigated by Decision 4 failing soft: a short-timeout `curl` failure logs a clear warning and the container still starts into a usable `opencode` prompt (per the `opencode-local-model-provider` spec's unreachable-server requirement); the user restarts after starting their server.
- **`--add-host=host.docker.internal:host-gateway` extending reachability beyond just the one model server** → the container can reach any host-bound port, not only 8000, via that hostname. Accepted: this is the minimum Docker primitive that makes `host.docker.internal` resolve on Linux, and `claude-yolo` already runs with full default network egress (no `--network=none` anywhere today), so this is not a new category of exposure, only a new reachable destination (the host itself).
- **A placeholder `apiKey` value could be confused for a real secret if a user later points `MLX_BASE_URL` at a server that does check it** → mitigated by naming it `"not-needed"` rather than something that looks like a plausible key, and documenting in the README that `opencode-yolo` is for unauthenticated local servers.

## Migration Plan

Purely additive: no existing file's behavior changes for `claude-yolo` users (its image tag, volume, entrypoint, and script are untouched). New users symlink `opencode-yolo` onto `PATH` the same way `claude-yolo` is installed today. Rollback is deleting the two new files and reverting the `Dockerfile`/README diffs; no data migration, since `opencode-yolo-home` is a brand-new volume name.
