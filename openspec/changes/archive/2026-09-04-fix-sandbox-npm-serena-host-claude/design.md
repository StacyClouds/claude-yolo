## Context

See `proposal.md` for motivation. Relevant current state:

- `Dockerfile` has a `builder` stage (git+ssh, needed only to add private plugin marketplaces via `docker build --ssh default` and run `claude plugin install`) whose `/home/node/.claude` and `/home/node/.claude.json` are copied into the final image.
- The final image runs `npm install -g @anthropic-ai/claude-code @fission-ai/openspec` as **root**, then later does `chown -R node:node /home/node` (after the `openspec init` bake step) before switching to `USER node`. It never touches ownership of npm's global prefix (`/usr/local/lib/node_modules`, `/usr/local/bin`), which stays root-owned.
- The `claude-yolo` script mounts `$HOME/.claude/CLAUDE.md` read-only at container start (`CLAUDE_MD_MOUNT`), conditional on the file existing on the host.
- `/home/node` is also where the `claude-yolo-home` named Docker volume is mounted, persisting Claude's login/session state across runs. A bind mount at a subpath of `/home/node` (e.g. `/home/node/.claude`) layers on top of that volume, the same way the existing `CLAUDE_MD_MOUNT` already does for one file.
- The `serena` plugin's MCP server is a Python package started via `uvx` (per its upstream install instructions); the final image has no Python or `uv`, so that process can never launch, which is why the MCP connection fails.
- The reported npm failure ("npm folder is read only") matches the global-prefix-ownership gap above: any `npm install -g` run as the unprivileged `node` user fails because it can't write to a root-owned directory.
- The `claude-yolo` script currently hardcodes `PROJECT_DIR` to `$SCRIPT_DIR/..` (the script's own parent directory) and mounts it as `/workspace`. Every invocation runs `docker run -it --rm ...`: a fresh, throwaway container per run, not a long-lived one you attach to. Login/session state persists independently via the `claude-yolo-home` named volume, unaffected by `--rm`.

## Goals / Non-Goals

**Goals:**
- Make `serena`'s MCP server actually able to start inside the sandbox.
- Make `npm install -g` (and npm's cache) work for the `node` user at runtime, not just during the root-run build steps.
- Replace the single-file `CLAUDE.md` mount with a read-only mount of the whole host `~/.claude` folder, and drop build-time plugin baking now that plugin config comes from the host.
- Let the workspace folder be chosen at runtime, without a rebuild.

**Non-Goals:**
- Preserving write access from inside the sandbox to the host's `~/.claude` folder (explicitly rejected in favor of read-only, matching the sandbox's existing "can't touch host state" model).
- Merging/overlaying host `~/.claude` content with the build-time baked opsx tooling (e.g. via an entrypoint sync step) so both are always available simultaneously. Out of scope for this change; the trade-off (host mount shadows the bake) is accepted and documented in the `sandbox/opsx-tooling` delta.
- Fixing npm permissions for arbitrary mounted project directories under `/workspace` (host-UID-vs-container-UID mismatches). Only the reported symptom - npm's own global folder being unwritable - is in scope.
- Changing how `claude-yolo-home` persists login/session state.
- Supporting multiple simultaneous workspaces inside a single running container. Concurrency is handled the way it already is today - by running the script twice, once per container - not by making one container serve multiple workspaces.

## Decisions

**Drop the `builder` stage entirely, rather than keeping it as a fallback.** Its only purpose was baking plugins via SSH-authenticated marketplace access. With plugin config now sourced from the host's mounted `~/.claude`, there's nothing left for it to do. This also removes `--ssh default` from `build_image` in the `claude-yolo` script and the private-repo SSH dependency at build time. Alternative considered: keep it as a fallback for when the host has no `~/.claude` (per the "keep both" option) - rejected per the user's explicit choice to replace rather than dual-maintain.

**Mount the whole `~/.claude` folder read-only at `/home/node/.claude-host`, and have an `entrypoint.sh` copy a fixed list of config items (`CLAUDE.md`, `settings.json`, `settings.local.json`, `agents`, `commands`, `skills`, `plugins`, `rules`, `keybindings.json`, `statusline-command.sh`, `statusline-command.ps1`, `workflows`) from there into the writable `/home/node/.claude` on every container start**, conditional on the host folder existing, mirroring the existing missing-folder fallback for `CLAUDE.md`. Originally this mounted read-only directly onto `/home/node/.claude` (the same path the image used to bake it, analogous to the old `CLAUDE_MD_MOUNT`) — that was simpler, but it shadowed the *entire* path read-only, including the runtime state Claude Code itself needs to write there (`.credentials.json`, session/conversation history, project trust decisions, todos, shell snapshots), which had previously persisted on the `claude-yolo-home` volume. That broke login: with no host `~/.claude`, none of these could be persisted at all, and every fresh container required logging in again. The entrypoint-sync approach keeps the read-only guarantee for the host's own copy (the container only ever reads `.claude-host`, never writes back to it) while leaving Claude's own runtime state on the writable volume, untouched by the sync. Alternative considered: reconfigure Claude Code's config directory (`CLAUDE_CONFIG_DIR`) to point somewhere else entirely - rejected because that's a single directory, so it can't source config from the host mount and also persist runtime state on the volume at the same time; the split copy-list is what actually lets both coexist.

**Fix npm's global install location by giving the `node` user ownership of npm's global prefix**, rather than reconfiguring npm to use a different `prefix` under `$HOME`. Chowning `/usr/local/lib/node_modules`, `/usr/local/bin`, and `/usr/local/share` (or whichever subset `npm config get prefix` resolves to in the `node:22-bookworm-slim` image) to `node:node` in the final build stage, after the root-run global installs, keeps the existing global binary paths and `PATH` untouched. Alternative considered: set `npm config set prefix ~/.npm-global` and add it to `PATH` - works too, but changes where globally-installed binaries live and adds a `PATH` edit; chowning the existing location is a smaller diff.

**Leave the `openspec` npm package install untouched in the final stage.** It's already installed globally there (`npm install -g @anthropic-ai/claude-code @fission-ai/openspec`), independent of the `builder` stage being removed and independent of the opsx-tooling bake (which only adds Claude-facing commands/skills under `~/.claude`, not the CLI binary itself). No change needed beyond verifying it still works after the npm ownership fix in the section above, since `openspec init` in a mounted project must keep working regardless of what happens to `~/.claude`.

**Add Python + `uv` via the official `uv` install script (or Debian's `python3` + `pipx`/`uv` package if available) in the final image stage**, so `uvx` is on `PATH` for the `node` user. `uv` is the tool the `serena` plugin's MCP server documentation launches it with; this is additive and has no interaction with the git-removal isolation model (uv/Python aren't git). This turned out to be necessary but not sufficient — see the next decision.

**Pre-install serena at build time via a throwaway `git`-enabled stage, and have `entrypoint.sh` rewrite its plugin config to use that instead of the plugin's own `uvx --from git+...` invocation.** Adding `uv`/`uvx` alone (previous decision) doesn't actually get serena running: the plugin's shipped MCP config resolves its `git+https://github.com/oraios/serena` dependency by having `uv` shell out to a real `git` binary, which this sandbox's final image deliberately never has — so serena's MCP server can never even download, let alone start, directly contradicting this change's own goal. This was only discovered by actually running the plugin's real invocation inside a live container (`uvx --from git+... serena --version`), which failed at `git init` against the stub; it wasn't caught by task 3.1/3.2's narrower "is `uvx` on PATH" checks. Three fixes were considered:
- **Leave it broken and document the conflict** - simplest, but abandons this change's stated goal for serena with a straightforward fix available.
- **A runtime `git` wrapper that allows some operations but not others** - rejected. A subcommand allowlist (block `commit`/`push`/`reset`/etc., allow `fetch`/`clone`/`init`/...) is brittle: it has to track whatever git subcommands `uv` happens to invoke, which isn't a stable public contract. A path-scoped wrapper (only allow git to operate within a dedicated scratch directory, refuse `-C`/`--git-dir`/`--work-tree`/`GIT_DIR`/`GIT_WORK_TREE` overrides and anything outside that prefix) is a more defensible property, but it's still a shell-script-enforced policy with real bypass surface (symlink swaps, argument-parsing edge cases) to get right - qualitatively weaker than today's "the binary doesn't exist," for a benefit (letting arbitrary future git+ tools resolve at runtime) this change doesn't actually need.
- **Pre-install serena once at build time, in a stage with a real (throwaway) `git`, and copy only the installed output into the final image** - chosen. It's a public repo, so this needs no SSH/credentials (unlike the plugin-marketplace `builder` stage removed elsewhere in this change). The final image still has zero working `git`, so the isolation guarantee stays exactly as strong and exactly as simple to verify ("the binary doesn't exist") as it is today. The trade-off is that serena's version is now pinned to whatever `serena-builder` fetched at the last `claude-yolo rebuild`, rather than updating on every container start the way `uvx` normally would - acceptable, since Claude Code itself is already pinned the same way in this image.

`entrypoint.sh` targets the rewrite narrowly (only a `.mcp.json` whose `serena` entry is exactly `{"command": "uvx", "args": [..., "git+https://github.com/oraios/serena", ...]}`) rather than blanket-replacing every `serena` key it finds, so a future marketplace update that changes serena's invocation shape is left alone instead of being silently overwritten with a now-stale rewrite.

**Parse `--workspace <path>` as a flag that must precede the subcommand** (e.g. `claude-yolo --workspace /path run ...`), rather than allowing it after the subcommand or mixed in with pass-through args. Args after the subcommand (or after `claude-yolo` itself in the no-args/yolo default) are already forwarded verbatim to the `claude` invocation inside the container; letting `--workspace` appear there too would make it ambiguous whether `--workspace` was meant for the script or for `claude` itself. Requiring it up front keeps the existing pass-through behavior completely unchanged. Resolve the given path with `cd "$path" && pwd` so it fails clearly (and before any container starts) if the path doesn't exist or isn't a directory. `rebuild` and `nuke` accept and simply ignore `--workspace` if given, since neither mounts a workspace - no need to error, since it's harmless. Alternative considered: an env var (`CLAUDE_YOLO_WORKSPACE`) instead of/alongside a flag - rejected for this change since the user asked specifically for the path to be settable, and a single explicit mechanism is simpler than two.

**No change to container lifecycle.** Each `claude-yolo` invocation already creates and discards a container (`docker run -it --rm`); making the workspace path a runtime parameter is just another `-v` argument to that same call. Login/session persistence (`claude-yolo-home`) and the new host-`~/.claude` mount are unaffected and continue to be shared across every invocation regardless of which workspace path is given.

**Force `skipDangerousModePermissionPrompt: true` into the container-local `settings.json` after the host-config sync, unconditionally.** This is the same class of problem already solved for `permissions.blockReadsOutsideWorkingDirectories`: Claude Code persists acceptance of the "Bypass Permissions mode" dialog as a key in the global user `settings.json`, but the host-config sync fully replaces that file from the host's copy on every container start, silently discarding any acceptance recorded during a previous container's life — so the dialog reappeared on every single run instead of just once. Forcing the key back on after the sync, using the same read-modify-write `jq` pattern as the existing `blockReadsOutsideWorkingDirectories` fix, makes YOLO mode behave as advertised. Doing this unconditionally (not only when a host `~/.claude` is mounted) also means a container with no host config at all defaults to no dialog, rather than only fixing the problem for hosts that happen to have a `~/.claude` folder. Alternative considered: only force it inside the `if [ -d "$HOST_CLAUDE" ]` block, matching where the `blockReadsOutsideWorkingDirectories` fix lives — rejected because the underlying cause (a fresh container never having accepted the dialog before) applies with or without a host mount, and it costs nothing to fix both cases the same way.

## Risks / Trade-offs

- **[Risk]** The fixed config-item list in `entrypoint.sh` (`CLAUDE.md`, `settings.json`, etc.) can drift from whatever Claude Code actually treats as global config vs. runtime state as new versions add files under `~/.claude`. A newly-added *config* category not in the list simply won't be sourced from the host until the list is updated; conversely nothing outside the list can leak into the sync and clobber runtime state. → **Mitigation**: the list favors leaving new/unknown paths alone (treated as runtime state) rather than syncing them, since an unsynced config item degrades gracefully (host settings for that item are ignored) while an incorrectly-synced runtime file recreates the original login-loss bug. Revisit the list if a new host config category needs sourcing.
- **[Risk (resolved)]** ~~Mounting `~/.claude` read-only means Claude Code inside the sandbox can no longer write runtime state it normally keeps under `~/.claude`~~ - this is what actually caused the reported login loss (every fresh container required re-authenticating). Fixed by mounting the host folder at `/home/node/.claude-host` instead and syncing only known config items into the writable `/home/node/.claude` via `entrypoint.sh`; see the `host-claude-config` decision above and its new "Login and other sandbox-local runtime state persists across runs" requirement.
- **[Risk]** Once a host `~/.claude` is mounted, opsx commands/skills baked at build time are only available if the host's own `~/.claude` happens to include them. → **Mitigation**: documented as a new requirement on `sandbox/opsx-tooling`; no code mitigation in this change.
- **[Risk]** If the host has no `~/.claude` folder, the sandbox now has zero plugins configured (previously it always had `serena`, `context7`, `honeycomb`, etc. baked in). → **Mitigation**: none; accepted per the user's explicit "replace" choice. The sandbox still starts and functions without plugins.
- **[Risk]** The exact directories `npm config get prefix` resolves to inside `node:22-bookworm-slim` could differ from what's assumed here. → **Mitigation**: verify with `npm config get prefix` and `npm root -g` during implementation rather than hardcoding paths from memory.
- **[Risk]** serena's version is now pinned to whatever the `serena-builder` stage fetched at the last `claude-yolo rebuild`, rather than always resolving to the latest commit the way the plugin's own `uvx --from git+...` invocation would. → **Mitigation**: none needed beyond `claude-yolo rebuild` to pick up a newer serena - the same trade-off this image already accepts for its pinned Claude Code version.
- **[Risk]** The `entrypoint.sh` rewrite only recognizes one exact shape of serena's `.mcp.json` (`command: "uvx"` with a `git+https://github.com/oraios/serena` argument). If the marketplace changes that shape (a different URL, a version pin, extra args), the rewrite silently stops matching and serena's MCP server goes back to failing at `git init`, with no error surfaced anywhere pointing at why. → **Mitigation**: none beyond noticing the MCP connection fails again and updating the match/rewrite in `entrypoint.sh` to the new shape.
